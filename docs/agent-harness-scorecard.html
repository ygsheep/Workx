未闭环当前剩余的真实缺口
  • 🔴 CI 硬门禁存在 flaky 误拦（#118） — 同一用例 server: ring buffer replays missed events on reconnect 在 8 次 CI 首次运行中失败 3 次（37.5%），同 commit 重跑即由红转绿。
    → 根因：island_server.cpp:122-156 的 accept 循环里 handle_connection() 阻塞，而 transport_posix.cpp:105-115 在 accept() 成功后立刻关闭监听端点 → 整个服务连接期间端点上没有监听者，重连只能靠 connect() 的 600ms 固定重试（6×100ms）撞运气。次要缺陷：测试 read_until 在 read 立即失败时不 break，空转满 3 秒，掩盖真因。
    → 建议：让 listen socket 生命周期内保持开放（AF_UNIX 常规做法），从根本上消除窗口。见 docs/p0-test-plan.md 阶段 6.3 / #118。
  • 🔴 #78 行为统计验收口径：已实测，未达标 — 原始标准是「结束前执行过测试/构建命令的比例 ≥90%」，首轮实测 6.7%（1/15）。#117 保持打开。
    → ⚠️ 别误读成「agent 不验证」：逐条 dump 命令显示它确实用 python3 -c / od -c / probe*.sh 在自检，问题是验证行为没规范化成可识别的构建/测试命令。
    → 🔴 更根本：Terminal-Bench 的 verifier 测试跑在独立容器里，agent 容器内拿不到 tests/，所以「跑可识别的测试运行器」这个口径在「空目录做题」场景下先天不适用 → 已开 #132，含「口径分场景」建议（尚未拍板）。
  • ⚠️ 45% 只能说明「能跑通」，不能说「达成」 — 首轮跑分已跑完（Harbor adapter + terminal-bench@2.0 20 题 × 1），但 -k 1 单次采样无置信区间、无对照组（harness 与模型贡献分不开）、选题是容量排除后按字母序取前 20（非随机）。
    → 要坐实分数：更大随机子集 + -k 3 + Claude/GPT 对照组，并画成本–成功率 Pareto 前沿（HarnessTax：harness 更影响成本，最高 5 倍）。
  • ⚠️ 4/20 轨迹为 0 字节（观测盲区） — agent 撞任务超时被强杀 → 容器销毁 → tee 的 workx-stream.jsonl 没取回。这 4 个不是「没验证」，是「不知道它做了什么」，已从验证类分母剔除（其中 3 个 verifier 反而判了通过）。
    → 讽刺的是：跑得最久、最可能撞超时的题恰恰最看不到。建议 agent 端定期 flush + 退出前落盘，或用 Harbor --artifact 回收。
  • #106 Windows ctest 中文测试名 — 196 / 1319 必然失败（与该批次含中文名用例数精确吻合）。ctest 把中文测试名当过滤参数传给测试进程时 argv 被 GBK 破坏。仅影响 Windows 本地，不阻塞已生效的 Linux 硬门禁。
